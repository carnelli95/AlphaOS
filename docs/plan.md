# AlphaOS 분석 및 발전 방향 설계

Nov 11, 2026 · @성훈

## 핵심 결론

AlphaOS는 개인 투자 도구로 유지하고, 밖으로 공개하는 것은 코드와 검증 리포트뿐이다. 새 정체성은 "투자 서비스"가 아니라 "검증까지 해본 기업 평가 엔진"이다.

남이 쓰는 서비스로 공개하지 않는 이유는 세 가지다.

- **겸직**: 공무원이 수익 서비스를 운영하면 겸직허가 문제가 생길 수 있다. 금공 입사 후에도 비슷한 제약이 있다.
- **규제**: 종목 정보를 유료로 제공하면 유사투자자문업 신고 대상이 될 수 있다. 정확한 판단은 전문가 확인이 필요하다.
- **운영 부담**: 데이터 장애 하나가 신뢰 문제로 번진다. 운영·유지보수를 싫어하는 성향과 정면으로 충돌한다.

## 지금까지 만든 것

데이터 수집부터 AI 리포트까지 파이프라인의 뼈대는 완성돼 있고, 미완성은 뉴스 이벤트(Stage D)와 자동 수집 가동 두 곳이다. 아래는 이전 대화에서 공유한 내용 기준이며, 코드로 직접 확인한 것은 아니다.

| 층 | 만든 것 | 상태 |
| --- | --- | --- |
| 데이터 수집 | DART·FinanceDataReader로 KOSPI 946종목, 재무 레코드 23,316건 적재 (PostgreSQL) | 작동, 맥 이전 완료 |
| 자동화 | Celery·Redis 일일 수집, 평일 16:30 스케줄 | 설정만 함, 아직 안 켬 |
| Stage A | 재무 데이터 처리 | 작동 |
| Stage D | 뉴스 이벤트 분석 | 버그: 모든 종목 1.25점 동일 |
| 팩터 스코어링 | PBR + ROE 복합 점수 | 작동, 초기 IC +0.21 |
| Stage E | LLM 리포트 생성 | 작동 |
| 프론트엔드 | Next.js + FastAPI | 로컬 작동 |
| 설계 원칙 | Signal-before-LLM: 계산은 파이썬, LLM은 설명만 | 유지할 가치 있음 |

### IC +0.21에 대한 솔직한 평가

가치 팩터 하나로 IC +0.21은 지나치게 높다. 실력보다 데이터 문제를 먼저 의심해야 한다.

1. **미래 정보 혼입**: 재무 데이터를 실제 공시일이 아닌 회계기간 기준으로 썼다면, 당시엔 알 수 없던 정보로 미래 수익률을 맞힌 셈이다.
2. **생존 편향**: 현재 상장된 946종목만으로 과거를 검증하면, 상장폐지 종목이 빠져 결과가 좋게 나온다.

이건 실패가 아니라 기회다. 약점으로 꼽았던 "자동화된 결과 검증"을 직접 발견하고 고치는 과정이 가장 좋은 포트폴리오 이야기가 된다.

## 기보 지원과의 연결

AlphaOS는 기보 기술평가 업무의 축소판이다. AlphaOS는 공시 재무데이터로 기업을 평가하고, 점수를 통계로 검증하고, AI로 리포트를 쓴다. 기보는 기업의 재무와 기술을 평가해 보증을 결정한다.

면접에서 쓸 문장은 "투자 사이트를 만들었습니다"가 아니라 이것이다.

> DART 데이터로 기업 평가 모델을 만들고, 그 결과가 진짜인지 통계로 검증해봤습니다.

## 목표 우선순위와의 연결

목표 순서는 1순위 대기업 AI 직무, 2순위 금공(기보 AI·데이터), 3순위 개발 업무다. AlphaOS의 각 단계는 세 목표 모두에 쓰이고, 강조하는 각도만 다르다.

| 단계 | AI 직무 (1순위) | 금공 (2순위) | 개발 업무 (3순위) |
| --- | --- | --- | --- |
| 0단계 재파악 | 시스템 전체 이해 | 시스템 전체 이해 | 아키텍처 문서화 |
| 1단계 검증 | 결과 검증 능력 | 기업 평가의 신뢰성 | 테스트·재현성 |
| 2단계 포트폴리오 | 배포까지 끝낸 AI 시스템 | 검증된 평가 엔진 | 운영·배포 경험 |

모델링 깊이는 AlphaOS만으로 부족하므로 데일리패션(의류 추천)이 AI 직무 쪽을 보강한다. 1순위로 가는 길은 신입 공채 직행과, 금공 AI·데이터 경력 후 경력직 이직 두 가지다.

## 발전 단계

재직하면서 할 수 있는 규모로, 3단계로 나눠 진행한다.

1. **0단계: 다시 파악하기 (임용 전 2\~3주)**
   - 3개월 만에 다시 보는 것이라 내가 뭘 만들었는지 모르는 게 당연하다. Claude Code에게 저장소 지도를 그리게 한다.
   - 요청 예시: "이 저장소 전체를 읽고 ARCHITECTURE.md를 만들어줘. 각 Stage의 입력·출력·관련 파일·DB 테이블·실행 방법, 미완성이거나 깨진 부분을 표로 정리해줘."
   - Celery beat를 켜서 데이터가 매일 쌓이는지만 확인한다.
2. **1단계: 숫자를 믿게 만들기 (1년차, 주 2\~3시간)**
   - IC를 재검증한다. 재무 데이터는 공시일 기준을 적용하고, 상장폐지 종목 처리 방식을 명시한다.
   - Stage D는 고치지 말고 일단 꺼둔다. 범위를 줄이는 것도 설계다.
   - IC가 0.03으로 떨어져도 괜찮다. 정직한 숫자라면 그 자체로 좋은 이야기다.
3. **2단계: 포트폴리오로 정리 (2년차)**
   - GitHub 저장소를 README·아키텍처 문서·실행 방법 중심으로 정리한다. 투자 신호 결과는 공개하지 않는다.
   - 검증 리포트를 기술 블로그 글 한 편으로 쓴다. 예: "IC +0.21이 왜 착시였고, 어떻게 고쳤나".
   - 기보 공고가 뜨면 이 글이 면접의 핵심 자료가 된다.

**보류**: B2B API, 자동매매, 공동창업자 모집 같은 사업 로드맵 2\~3단계는 지금의 공무원·금공 경로와 충돌한다. 창업을 결심할 때 다시 꺼낸다.
